### 移除图片发送前压缩功能
- **问题**：添加 `lib/image-utils.ts` 的 `compressImages` 后，发送图片消息报 HTTP 400。
- **根因**：`compressImages` 调用 `compressImage(img.previewUrl)`，但 `previewUrl` 是 `blob:` 类型的 Object URL，而 `compressImage` 内部期望 `data:` 类型的 Base64 Data URL。`blob:` URL 无法被正确解析，导致压缩逻辑异常。
- **操作**：
  1. 删除 `hooks/useAgentSession.ts` 中对 `compressImages` 的导入。
  2. 删除 `handleSend` 中的压缩逻辑块，恢复为直接使用原始 `images`。
  3. 删除不再使用的 `lib/image-utils.ts` 文件。
- **状态**：已完成，需重启项目生效。

### 修复发送图片报 400 错误（空白气泡问题）
- **现象**：删除压缩代码后仍无法发送图片，发送后 AI 回复为空白气泡。用户反馈后台返回 400。
- **根因分析**：
  1. `rpc-manager.ts` 中 `.catch(() => {})` 把 LLM API 错误静默吞掉，导致前端只能收到一个 `content: [{text: ""}]` 的空消息（`pi-agent-core` 的 `handleRunFailure` 行为），表现为空白气泡。
  2. 只发图片时 `message` 为空字符串，构造的 user content 为 `[{type: "text", text: ""}, {type: "image", ...}]`。部分 LLM provider（包括 Kimi 兼容接口）对空字符串 text block 会返回 400 Bad Request。
  3. `FileReader.readAsDataURL` 返回的 base64 在某些浏览器/剪贴板场景下可能包含换行符，也会导致 API 解析失败。
- **修复操作**：
  1. `components/ChatInput.tsx`：提取 base64 时用 `.replace(/\s/g, "")` 去除所有空白字符（换行符、空格）。
  2. `hooks/useAgentSession.ts`：当只发送图片（`message.trim()` 为空）时，自动把 `message` 替换为 `"(see attached image)"`，避免向 LLM 发送空字符串 text block。
  3. `lib/rpc-manager.ts`：把 `.catch(() => {})` 改为 `.catch((err) => { console.error("Agent prompt failed:", err); })`，让错误信息至少打印到服务端控制台。
- **状态**：TypeScript 编译通过，需重新运行 `setup.bat` 生效。

### 深入排查图片发送仍失败（空气泡 + HTTP 500）
- **现象**：用户重新 build 后仍无法发送图片，AI 回复为空白气泡，浏览器开发者工具显示 HTTP 500。
- **关键日志分析**：
  - 服务端日志显示 `[RPC] prompt command, message: (see attached image) images count: 1`，说明前端成功把图片数据传到了 RPC 层。
  - 日志中没有 `[RPC] Agent prompt failed:` 或 `[API ...] Error:`，说明 API 路由本身没有抛 500。
- **空白气泡的根因确认**：
  - `pi-agent-core/dist/agent.js` 中 `runWithLifecycle` 的 catch 块会捕获 LLM API 的所有异常，然后调用 `handleRunFailure`。
  - `handleRunFailure` 生成一个 `content: [{type: "text", text: ""}]` 的 failureMessage，然后通过事件流发送给前端。
  - 这就是用户看到的"空气泡"的来源——LLM API 调用失败，但错误被内部消化，前端只能看到一个空消息。
- **HTTP 500 的可能来源**：
  - 由于 `/api/agent/[id]` 路由没有抛 500，500 很可能来自 `GET /api/sessions/[id]`（`agent_end` 后 `loadSession` 触发的请求）。
  - `app/api/sessions/[id]/route.ts` 之前没有错误日志，已在 catch 块中添加 `console.error`，以便下次测试时确认。
- **待排查方向**：
  1. 用户使用的是**已有会话**（日志显示 `Existing session alive`）。如果会话历史中有损坏的图片数据，LLM API 在发送完整历史时可能会失败。
  2. 需要用户在**全新会话**中测试，以区分是"历史数据问题"还是"发送逻辑问题"。
  3. 需要用户提供浏览器 Network 面板中 500 请求的具体 URL 和响应体。

### 最终修复：旧会话历史中的空文本块导致 400
- **关键测试结论**：用户在**全新会话**中能正常发送图片，确认问题出在旧会话的历史数据上。
- **根因确认**：通过脚本检查会话文件，发现旧会话中存在 `{"type":"text","text":""}` 的空文本块。当 LLM API 接收包含空文本块的完整历史时，会返回 400 Bad Request。
- **空文本块的来源**：添加压缩功能前，代码在构造 user content 时没有过滤空字符串 text block。只发图片时会产生 `[{"type":"text","text":""},{"type":"image",...}]` 的结构，这个结构被持久化到了会话文件中。
- **修复方案**：修改 `lib/normalize.ts` 中的 `normalizeToolCalls` 函数，添加 `cleanEmptyTextBlocks` 步骤。在从会话文件读取消息历史时，自动过滤掉 `type: "text"` 且 `text.trim() === ""` 的空文本块。这样无需修改原始会话文件，所有旧会话自动恢复可用。
- **状态**：TypeScript 编译通过，需重新运行 `setup.bat` 生效。

### 最终修复旧会话：彻底移除 [IMAGE_DATA_REMOVED...] 占位符
- **根因确认**：旧会话文件 `2026-05-29T13-14-18-300Z_019e73df-0d3c-738b-b7f1-bb273315d1d2.jsonl` 中有 81 个 `[IMAGE_DATA_REMOVED_...chars]` 图片占位符。这些是 `lib/clean-session.ts` 的 `cleanSessionImages` 函数在自动清理大图片时产生的。pi-coding-agent 会把这些占位符当成真实 base64 图片数据发给 LLM，LLM 收到无效的 base64 后返回 400。
- **修复方案**：

     - 新增 `fixRemovedImagePlaceholders(filePath)` 函数，遍历会话文件的每一行，过滤掉所有包含 `[IMAGE_DATA_REMOVED` 的 image block。
  2. **修改 `app/api/agent/[id]/route.ts`**：在 `startRpcSession` 加载会话之前，自动调用 `fixRemovedImagePlaceholders`，修复旧会话中的占位符。
  3. **修改 `app/api/agent/[id]/events/route.ts`**：同上，确保 events 流加载会话时也自动修复。
  4. **保留 `lib/normalize.ts` 的过滤逻辑**：作为双重保险，前端显示历史消息时也会过滤掉空文本块和占位符。
- **状态**：TypeScript 编译通过，需重新运行 `setup.bat` 生效。
